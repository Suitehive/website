**What you'll learn:** how to go from an empty folder to all three Suitehive apps running on your machine with demo data, and how to make your first change.

You will open several terminals: one for each service (Auth, Mail, Calendar) and one for each web app. Every command runs from the workspace root, the folder that holds `go.work`.

## Before you start

| Tool | Version | Check with |
|---|---|---|
| Git | any recent version | `git --version` |
| Go | 1.27 (every `go.mod` says `go 1.27`) | `go version` |
| Node.js | 24, with the npm that ships with it | `node --version` |
| Docker Desktop | with Docker Compose v2 | `docker compose version` |

```text title="Output (example)"
go version go1.27.0 windows/amd64
v24.15.0
```

<Aside type="note" title="Which shell?">
On macOS and Linux, use any POSIX shell. On Windows, use PowerShell or Git Bash. The commands in the `RUN.md` file of each repository use Git Bash syntax. This page shows both where they differ.
</Aside>

## Get it running

<Steps>

1. **Clone the workspace and the repositories.**

   The workspace root is the [architecture](https://github.com/Suitehive/architecture) repository. It already contains `go.work` (links the Go modules) and a root `package.json` (an npm workspace for the web apps and UI packages). Clone it, then clone the other repositories inside it, side by side.

   <Tabs syncKey="os">
   <TabItem label="macOS / Linux">

   ```sh
   git clone https://github.com/Suitehive/architecture.git suitehive
   cd suitehive
   for r in kit contracts ui auth mail calendar deploy; do
     git clone "https://github.com/Suitehive/$r.git"
   done
   for r in ui auth mail calendar; do git -C "$r" switch wip/2026-10-13; done
   npm install
   ```

   </TabItem>
   <TabItem label="Windows (PowerShell)">

   ```powershell
   git clone https://github.com/Suitehive/architecture.git suitehive
   cd suitehive
   foreach ($r in 'kit','contracts','ui','auth','mail','calendar','deploy') {
     git clone "https://github.com/Suitehive/$r.git"
   }
   foreach ($r in 'ui','auth','mail','calendar') { git -C $r switch wip/2026-10-13 }
   npm install
   ```

   </TabItem>
   </Tabs>

   <Aside type="caution" title="Why the wip branch">
   The integrated version that runs end to end (including the `RUN.md` files) is on the `wip/2026-10-13` branch of `ui`, `auth`, `mail` and `calendar`. It will be merged into `main`. After that, skip the `switch` line.
   </Aside>

   **If this fails:** the repositories are private for now. If `git clone` asks for credentials or returns "Repository not found", ask a maintainer for access to the [Suitehive organization](https://github.com/Suitehive).

2. **Start Postgres and NATS.**

   ```sh
   docker compose -f deploy/dev/docker-compose.yml up -d
   docker compose -f deploy/dev/docker-compose.yml ps
   ```

   ```text title="Output"
   NAME                       IMAGE         ...   STATUS
   suitehive-dev-nats-1       nats:2.11     ...   Up
   suitehive-dev-postgres-1   postgres:17   ...   Up (healthy)
   ```

   On first start, an init script creates the databases `suitehive_auth`, `suitehive_mail` and `suitehive_calendar` (user and password `suitehive`).

   **If this fails:** make sure Docker Desktop is running. If port 5432 or 4222 is taken, stop the other Postgres or NATS first; the compose file uses fixed ports.

3. **Run Auth (terminal 1).**

   <Tabs syncKey="os">
   <TabItem label="macOS / Linux">

   ```sh
   SH_DEV_SEED=true SH_DEV_INSECURE_COOKIES=true go run ./auth/cmd/auth
   ```

   </TabItem>
   <TabItem label="Windows (PowerShell)">

   ```powershell
   $env:SH_DEV_SEED = 'true'
   $env:SH_DEV_INSECURE_COOKIES = 'true'
   go run ./auth/cmd/auth
   ```

   </TabItem>
   </Tabs>

   `SH_DEV_SEED=true` creates the org **Demo**, the domain `suitehive.local` and three users. `SH_DEV_INSECURE_COOKIES=true` lets sign-in work over plain `http://localhost`. Check it from another terminal:

   ```sh
   curl -s http://localhost:8081/readyz
   ```

   ```text title="Output"
   {"checks":{"nats":"ok","postgres":"ok"},"status":"ok"}
   ```

   On Windows PowerShell, type `curl.exe` instead of `curl`.

   **If this fails:** a `postgres` or `nats` check that is not `ok` means step 2 is not running. Do not set `SH_DEV_TRUST_DOMAINS=true`: it is a list of domain names, not a switch, and `true` breaks mail delivery to `suitehive.local`.

4. **Run Mail (terminal 2).**

   <Tabs syncKey="os">
   <TabItem label="macOS / Linux">

   ```sh
   SH_DB_URL='postgres://suitehive:suitehive@localhost:5432/suitehive_mail?sslmode=disable' \
   SH_NATS_URL=nats://localhost:4222 \
   SH_HTTP_ADDR=:8082 \
   SH_PUBLIC_URL=http://localhost:8082 \
   SH_AUTHN_ISSUER=http://localhost:5171 \
   SH_AUTHN_JWKS_URL=http://localhost:8081/jwks \
   SH_AUTHN_AUDIENCE=mail \
   SH_AUTH_RPC_URL=http://localhost:8081 \
   SH_TOKEN_URL=http://localhost:8081/oauth2/token \
   SH_CLIENT_ID=svc:mail SH_CLIENT_SECRET=dev-secret-mail \
   SH_BLOB_DIR=var/mail-blobs \
   SH_SMTP_ADDR=:2525 SH_SUBMISSION_ADDR=:2587 SH_IMAP_ADDR=:1143 \
   SH_DEV_SEED=true \
   SH_LOG_FORMAT=text \
   go run ./mail/cmd/mail
   ```

   </TabItem>
   <TabItem label="Windows (PowerShell)">

   ```powershell
   $env:SH_DB_URL = 'postgres://suitehive:suitehive@localhost:5432/suitehive_mail?sslmode=disable'
   $env:SH_NATS_URL = 'nats://localhost:4222'
   $env:SH_HTTP_ADDR = ':8082'
   $env:SH_PUBLIC_URL = 'http://localhost:8082'
   $env:SH_AUTHN_ISSUER = 'http://localhost:5171'
   $env:SH_AUTHN_JWKS_URL = 'http://localhost:8081/jwks'
   $env:SH_AUTHN_AUDIENCE = 'mail'
   $env:SH_AUTH_RPC_URL = 'http://localhost:8081'
   $env:SH_TOKEN_URL = 'http://localhost:8081/oauth2/token'
   $env:SH_CLIENT_ID = 'svc:mail'
   $env:SH_CLIENT_SECRET = 'dev-secret-mail'
   $env:SH_BLOB_DIR = 'var/mail-blobs'
   $env:SH_SMTP_ADDR = ':2525'
   $env:SH_SUBMISSION_ADDR = ':2587'
   $env:SH_IMAP_ADDR = ':1143'
   $env:SH_DEV_SEED = 'true'
   $env:SH_LOG_FORMAT = 'text'
   go run ./mail/cmd/mail
   ```

   </TabItem>
   </Tabs>

   The dev seed sends about 33 demo messages to `priya@` and `alex@suitehive.local` through the real inbound pipeline. Look for these log lines:

   ```text title="Output (log lines to look for)"
   directory read-model bootstrapped from auth snapshot
   dev seed: demo mail queued for delivery messages=33 users=2
   ```

   ```sh
   curl -s http://localhost:8082/readyz
   ```

   ```text title="Output"
   {"checks":{"jwks":"ok","nats":"ok","postgres":"ok"},"status":"ok"}
   ```

   **If this fails:** a `jwks` check that is not `ok` means Mail cannot reach Auth on port 8081. Start Auth first. If you reset the Auth database earlier, also drop and recreate `suitehive_mail` (see [Debug a service](/docs/developers/recipes/debugging/)).

5. **Run Calendar (terminal 3).**

   <Tabs syncKey="os">
   <TabItem label="macOS / Linux">

   ```sh
   SH_DEV_SEED=true go run ./calendar/cmd/calendar
   ```

   </TabItem>
   <TabItem label="Windows (PowerShell)">

   ```powershell
   $env:SH_DEV_SEED = 'true'
   go run ./calendar/cmd/calendar
   ```

   </TabItem>
   </Tabs>

   With `SH_PUBLIC_URL` unset, Calendar uses local defaults that match Auth and Mail on their usual ports. It applies its migrations, waits for Auth's user events, creates calendars and seeds demo events. The log line `dev seed complete` marks the end.

   ```sh
   curl -s http://localhost:8083/readyz
   ```

   ```text title="Output"
   {"checks":{"jwks":"ok","nats":"ok","postgres":"ok","realtime":"ok"},"status":"ok"}
   ```

   **If this fails:** if the seed never completes, check that Auth is running with `SH_DEV_SEED=true`. Calendar waits for the demo users to arrive as events from Auth.

6. **Start the web apps (terminals 4, 5 and 6).**

   <Tabs syncKey="os">
   <TabItem label="macOS / Linux">

   ```sh
   # terminal 4: sign-in, account and admin (http://localhost:5171)
   VITE_API_MODE=live VITE_AUTH_WEB_URL=http://localhost:5171 \
   VITE_MAIL_WEB_URL=http://localhost:5172 VITE_CALENDAR_WEB_URL=http://localhost:5173 \
   npm run dev -w auth/web

   # terminal 5: Mail (http://localhost:5172/mail)
   VITE_API_MODE=live VITE_AUTH_WEB_URL=http://localhost:5171 \
   VITE_MAIL_WEB_URL=http://localhost:5172 VITE_CALENDAR_WEB_URL=http://localhost:5173 \
   npm run dev -w mail/web

   # terminal 6: Calendar (http://localhost:5173/calendar)
   VITE_API_MODE=live VITE_AUTH_WEB_URL=http://localhost:5171 VITE_MAIL_WEB_URL=http://localhost:5172 \
   npm run dev -w calendar/web
   ```

   </TabItem>
   <TabItem label="Windows (PowerShell)">

   ```powershell
   # run these four lines in each web terminal
   $env:VITE_API_MODE = 'live'
   $env:VITE_AUTH_WEB_URL = 'http://localhost:5171'
   $env:VITE_MAIL_WEB_URL = 'http://localhost:5172'
   $env:VITE_CALENDAR_WEB_URL = 'http://localhost:5173'

   npm run dev -w auth/web       # terminal 4
   npm run dev -w mail/web       # terminal 5
   npm run dev -w calendar/web   # terminal 6
   ```

   </TabItem>
   </Tabs>

   Each Vite server prints its address, for example:

   ```text title="Output"
   Local:   http://localhost:5172/
   ```

   Vite forwards `/api/auth`, `/api/mail`, `/api/calendar` and the other API paths to ports 8081, 8082 and 8083. The browser sees one origin, so cookies and CSRF checks work.

   **If this fails:** the dev scripts use `--strictPort`, so Vite stops if the port is in use. Close the other process on 5171, 5172 or 5173. You can also put the `VITE_*` values in a `.env.local` file in each web folder.

7. **Sign in with a demo account.**

   Open [http://localhost:5171/login](http://localhost:5171/login). Every demo account uses the password `suitehive-dev`.

   | Email | Role | Try |
   |---|---|---|
   | `admin@suitehive.local` | owner | the admin console at http://localhost:5171/admin |
   | `priya@suitehive.local` | member | the inbox at http://localhost:5172/mail (she has demo mail) |
   | `alex@suitehive.local` | member | the calendar at http://localhost:5173/calendar |

   **If this fails:** if sign-in loops back to the login page, check that Auth runs with `SH_DEV_INSECURE_COOKIES=true`. Without it, Auth sets `__Host-` cookies, which browsers only accept over HTTPS.

8. **Make a change and watch it hot-reload.**

   Open `auth/web/src/features/sign-in/components/login-form.tsx` and change `title="Sign in"` to `title="Sign in to Suitehive"`:

   ```tsx title="auth/web/src/features/sign-in/components/login-form.tsx"
   <EntryHeading title="Sign in to Suitehive">{step === 'password' && org?.orgName ? `to ${org.orgName}` : undefined}</EntryHeading>
   ```

   Save the file. The login page updates within a second, without a full reload. Undo it with `git -C auth checkout -- web/src/features/sign-in/components/login-form.tsx`.

   Go code does not hot-reload. After a Go change, stop the service with Ctrl+C and run the same `go run` command again.

</Steps>

<Aside type="tip" title="UI work without any backend">
Leave out `VITE_API_MODE=live` and the web apps use an in-memory mock API with demo data. From the workspace root, `npm run dev:mail` (or `dev:auth`, `dev:calendar`) is all you need.
</Aside>
